## 核心洞察总结

### 1. Scholar Ref Cleaner - 学术引用验证的黄金标准

**项目地址**：https://github.com/libo-huang/scholar-ref-cleaner

**核心问题**：
- ChatGPT/Claude 等生成式 AI 在写作时编造"幻觉文献"（Hallucinated References）
- 这些假文献看似真实（有作者、年份、期刊），但在学术数据库中根本不存在
- 对学术诚信构成严重风险

**解决方案**：
```
瀑布流验证策略（串行查询三大学术数据库）：
1. Google Scholar（覆盖最全）
2. Semantic Scholar（学术图谱质量高）
3. Crossref（出版商官方元数据）

若任一数据库找到匹配文献 → 验证通过
若三者均未找到 → 极可能是 AI 幻觉
```

**三级判定系统**：
- ✅ **Verified**（已验证）：相似度 >85%，元数据已自动修正，可直接使用
- ⚠️ **Ambiguous**（存疑）：相似度 50-85%，需人工复核
- ❌ **Not Found**（未找到）：三大数据库均无记录，极可能是幻觉

**关键设计思路**：
1. **后验证而非生成时约束**：不试图阻止 AI 生成内容，而是提供可靠的事实核查层
2. **宽容的匹配策略**：通过相似度阈值容忍小幅差异（标题措辞、年份偏差），减少误报
3. **优雅降级机制**：应对学术 API 的访问限制（如 Google Scholar CAPTCHA），自动切换备选数据库
4. **多格式支持**：BibTeX 直接修正、Word/Text 生成报告

**对我们的启发**：
- ✅ 我们也应该采用"后验证"模式：生成完成后审计，而非生成时干预
- ✅ 相似度阈值分级（>85% 可信、50-85% 存疑、<50% 风险）比二元判断更实用
- ✅ 需要外部知识库验证事实性主张（我们当前缺失）
- ❌ 我们目前只有熵值和一致性，无法验证"引用是否真实存在"

### 2. FactLite Issue #1 - 对现有方法的深刻批评

**Issue 地址**：https://github.com/SRInternet-Studio/FactLite/issues/1

**核心批评**：

#### 问题 1：Self-bias in Verification（自我偏差）
```
生成 LLM 和验证 LLM 能力相当时：
→ 共享相同的"参数化知识盲区"
→ 验证者无法识别生成者自己都不知道的错误
→ 理论上无效

反问：如果生成模型在 90k tokens 处出错（100k 上下文窗口），
相同的验证模型能发现吗？
```

#### 问题 2：检索质量差
- 用户问题直接当搜索 query，无 query rewriting 或 expansion
- 搜索结果无相关性过滤、去重、rerank
- 原始 top-k 结果直接拼接到 prompt
- 噪音污染上下文，线性增加 token 成本

#### 问题 3：控制流冲突
```
FactLite 的 @verify 装饰器：
→ 规则链短路失败 → 注入错误反馈 → 触发 LLM 重试

与 LangGraph 等编排框架冲突：
→ 外部装饰器强制修改输入并重新触发全图执行
→ 与内部状态机、检查点、节点级递归限制冲突
→ 导致逻辑混乱或静默失败
```

**提出的改进建议**：
1. **重新定位叙事**：放弃"幻觉解决"宣传，专注于"时效性验证"
2. **增强检索**：添加 query rewrite + rerank
3. **修复规则链**：从短路改为非短路评估，聚合结果后决策
4. **尊重编排**：不要与编排框架争夺控制流权限
5. **正确的简洁**：轻量级可以，但"五脏得全"

**对我们的启发**：
- ✅ 我们没有宣称"幻觉检测器"，已改为"可用性审计工具"（定位正确）
- ✅ 我们不做控制流干预，只提供审计报告（架构正确）
- ❌ 我们目前无外部知识验证能力
- ❌ 我们的一致性检测用 token 首次分叉判断，需改为语义相似度聚类
- ⚠️ 如果未来添加 RAG，必须做好：query rewrite、relevance filter、rerank

### 3. FactLite 项目 - 轻量级验证框架

**项目地址**：https://github.com/SRInternet-Studio/FactLite

**架构**：Generate → Evaluate → Reflect 循环
```python
@verify(config=config, user_prompt="question")
def generate_answer(prompt):
    return llm.chat(prompt)
```

**验证器插件**：
- `LLMJudge`：用独立模型（如 GPT-4）评判答案
- `Web_LLMJudge`：搜索 DuckDuckGo/Bing/Google 验证时效性
- `RegexValidator`：强制禁用词和必需模式
- `LengthValidator`、`JSONValidator`、`ModerationJudge`：结构和安全检查
- `CustomJudge`：任意 Python 逻辑（数据库查询、业务规则）

**性能指标**（AA-Omniscience 基准测试）：
- 幻觉率：63.5% → 16%（下降 47.5 个百分点）
- 全知指数：-27.50 → +16.00（提升 43.5 分）
- 统计显著性：p < 0.0001

**对我们的启发**：
- ✅ 插件化验证器架构很好，我们可以借鉴
- ✅ Web 搜索验证时效性主张（日期、事件、数字）
- ✅ 反射循环（Reflection）让 LLM 看到"这个错误是因为..."
- ❌ 但 Issue #1 指出的问题仍然存在：self-bias、检索质量差、控制流冲突
- ⚠️ 我们当前只做"后验证报告"，不做"生成时干预"，避开了控制流问题

### 4. NabaOS - 基于印度哲学的 AI 代理验证系统

**论文地址**：https://arxiv.org/html/2603.10060v1

**核心创新**：用印度哲学正理派（Nyāya）认识论分类 AI 声明的来源

#### Nyāya 六种认识来源（Pramāṇa）
1. **Pratyakṣa（现量）**：直接来自工具输出的声明
2. **Anumāna（比量）**：从工具数据推断出的内容
3. **Śabda（圣言量）**：引用的外部来源
4. **Abhāva（无体量）**：关于不存在的声明（如"未找到结果"）
5. **Upamāna（譬喻量）**：类比或比较
6. **Ungrounded**：无任何证据支持的意见

#### HMAC 签名工具执行凭证
```json
{
  "id": "唯一标识符",
  "tool_name": "工具名称",
  "input_hash": "SHA-256 哈希",
  "output_hash": "SHA-256 哈希",
  "result_count": 42,
  "facts": ["发件人: alice@example.com", "主题: Q3 Report"],
  "timestamp_ms": 1699123456789,
  "signature": "HMAC-SHA256 签名"
}
```

**防伪造机制**：
- ✅ LLM 无法访问 HMAC 密钥 → 无法构造虚假凭证
- ✅ 任何字段修改 → 签名失效
- ✅ 运行时为每个工具调用生成唯一凭证
- ✅ 提供完整的执行历史记录

**多层防护**：
1. **确定性检测**（不依赖 LLM 合作）：
   - 伪造工具调用：检查凭证 ID 是否存在
   - 数量不符：对比 LLM 声称的数量与凭证中的 result_count
   - 虚假"未找到"：检查凭证是否显示 result_count > 0

2. **自标注提示**：要求 LLM 为每个声明标注来源类型和证据
   - Claude 合规率：92%
   - 非合规响应 → 保守地标记为"完全无根据"

3. **深度代理交叉检查**：独立重新获取 URL、重放计算、检查时间一致性
   - 检测率：78.4%

**性能对比**（NyayaVerifyBench 基准测试）：

| 方法 | 检测率 | 误报率 | 延迟 | 成本/请求 |
|------|--------|--------|------|----------|
| 自洽性检查 | 45% | 12% | +3-5秒 | +$0.03 |
| RAG验证 | 52% | 18% | +1-2秒 | +$0.01 |
| SVIP风格 | 68% | 10% | +50毫秒 | $0 |
| **NabaOS** | **91%** | **4%** | **+12毫秒** | **$0** |

**信任校准**：
- 标记为"完全验证"的响应：98.7% 准确率
- 标记为"不可靠"的响应：23.4% 准确率
- 证明信任级别确实反映实际可靠性

**对我们的启发**：
- ✅ **认识来源分类**非常适合我们的审计报告：
  - 现量：来自检索到的文档段落
  - 比量：从段落推断出的主张
  - 圣言量：引用的具体文献
  - 无体量："未找到支持该主张的来源"
  - 无根据：模型自己编造的内容
- ✅ **HMAC 签名凭证**机制可用于我们的 trace 验证：
  - 每个 token 生成步骤带签名
  - 防止用户或攻击者篡改 trace 数据
  - 确保审计报告基于真实的生成过程
- ✅ **确定性检测优于 LLM 判断**：
  - 我们的熵值、时间序列异常检测是确定性的（好！）
  - 但一致性检测用 token 首次分叉是脆弱的（需改进）
- ✅ **信任校准**：我们应该测试"低熵标记"的实际准确率
  - 如果"低熵"标记的主张有 >95% 准确率 → 可以告诉用户
  - 如果只有 60% → 必须明确说明"低熵不等于正确"

## 核心设计原则（从参考项目中提炼）

### 1. 后验证而非生成时约束
- ✅ Scholar Ref Cleaner：生成完成后验证引用
- ✅ 我们的设计：生成完成后审计报告
- ❌ FactLite 的 @verify 装饰器：生成时干预（与编排框架冲突）

### 2. 确定性检测优于 LLM 判断
- ✅ NabaOS：HMAC 签名、数量对比、ID 检查（确定性）
- ✅ 我们的设计：熵值、时间序列异常（确定性）
- ❌ FactLite：用 LLM 判断 LLM（self-bias 问题）

### 3. 分级判定而非二元判断
- ✅ Scholar Ref Cleaner：已验证 / 存疑 / 未找到（三级）
- ✅ NabaOS：信任级别对应实际准确率（校准）
- ✅ 我们的设计：独立展示各维度，不做综合评分

### 4. 外部知识验证事实性
- ✅ Scholar Ref Cleaner：查询三大学术数据库
- ✅ FactLite：搜索引擎验证时效性
- ✅ NabaOS：重新获取 URL、重放计算
- ❌ 我们当前缺失：只有内部信号（熵值、一致性），无外部验证

### 5. 优雅降级和容错
- ✅ Scholar Ref Cleaner：Google Scholar CAPTCHA → 切换到 Semantic Scholar
- ✅ Scholar Ref Cleaner：相似度阈值容忍小幅差异
- ✅ NabaOS：LLM 不合规 → 保守地标记为"完全无根据"
- ⚠️ 我们需要添加：用户上传 PDF 失败 → 明确告知"无法解析"

### 6. 可审计和可追溯
- ✅ Scholar Ref Cleaner：导出 BibTeX、生成验证报告
- ✅ NabaOS：HMAC 签名凭证、完整执行历史
- ✅ 我们的设计：导出 JSON/Markdown、跳转到原文
- ⏳ 待改进：添加 HMAC 签名、保留页码边界
