# AOKS · Product Delivery Workflow（从需求到可信体验）

> 本文只回答：如何把一个需求做成“可探索的观察体验”，而非模板化 AI 页面或无证据的特效。
> 规范住址：原则 See Vol I；认知/视觉 See AODL；交互与 Motion See Vol III。

## 适用范围

视觉、交互、3D、动效、新模块、默认信息层级或影响用户理解的改动。纯 Bug、类型、测试和构建修复不必走完整流程，除非它改变体验语义。

## 六步工作流

### 1. 定义问题，不从组件开始

写一句用户问题：用户此刻想理解什么，或为什么会卡住？
明确服务层：Explorer（默认好奇与理解）、Researcher（原始证据）或 Builder（trace/workflow）。默认不得把 Researcher 面板直接当 Explorer 首页。

### 2. 做设计决策卡（实现前）

使用下方模板。若无法写出真实数据来源、用户获得的理解、或删掉效果后损失的信息，就不进入实现。

### 3. 先定静态信息层级，再定动态表达

先确定唯一主焦点、主动作和三级下潜；然后才讨论 motion。动效只能表达空间、时间、因果或注意之一，且必须由 runtime/trace 事件触发。

### 4. 进行多角色反驳

按 `DESIGN-REVIEW.md` 让 Explorer、研究者、产品负责人、视觉负责人分别挑错。不是收集漂亮意见，而是暴露误导、过载、假数据和不可验证的部分。

### 5. 实现与截图审查

实现时复用现有 token、组件状态、交互语法和 icon 规则。截图审查先看静态第一屏：是否仍像 Dashboard、赛博 AI 模板或数据墙？再看交互过程：焦点是否跟随真实事件？

### 6. 验证并写回

跑项目验证序列；更新必要的体验稿、测试与任务看板。若方案没有实现预期认知收益，记录失败并回到第 1 步，而不是用更多效果掩盖。

## 设计决策卡模板

```md
### <功能/改动名> · 设计决策卡
- 用户与场景：Explorer / Researcher / Builder；用户此刻的问题：
- 认知位置：接观察阶梯第几阶；下一阶钩子：
- 唯一主焦点与主动作：
- Question → Evidence → Interaction → Conclusion（用户产生）→ Replay：
- 真实数据来源：trace/测量字段、缺失时的诚实空态：
- 视觉映射：每个形状、颜色、空间位置、动效分别表达什么：
- 删除测试：删掉该视觉/动效后用户会失去什么信息：
- 渐进披露：默认层隐藏的专家字段与下潜路径：
- 风险：最可能误导、过载或做成假 UI 的方式：
- 验收：如何证明用户理解增加，而不是只觉得更炫：
```

## 不可跳过的底线

- 不用“AI 正在想/醒来/协作”替代具体可测的运行时事件。
- 不用 RGB、玻璃、渐变、粒子或 3D 弥补信息层级不清。
- 不以虚构 Agent、Memory、GPU 内部状态做首屏叙事；真实导入 trace 到来后才渲染。
- 不以“高级感”为理由绕过词表、可访问性、Reduced Motion 或真实数据来源。
